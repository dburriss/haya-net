# ADR018: Dependencies between annotated classes, walked through unannotated code, under `members`

Date: 2026-11-11  
Status: Accepted  
Author: dburriss

### Context
ADR017 gave each annotated class a `Uses`: the other annotated classes of its app whose name is exactly the type of one of
its constructor parameters. Real code rarely looks like that. A controller with a `[Collaborator]` calls a service with no
attribute, which calls a gateway, which calls the class whose `[Collaborator]` names the payment provider. That is the chain
readers want to see ("what does this entry point end up calling?"), and `Uses` misses all of it.

We want: when annotated class X reaches annotated class Y in code through any number of unannotated types, X -> Y is
recorded, with the types in between. This is a code dependency (caller to callee). It does not depend on which way a
collaborator's `Direction` points: an inbound controller reaching a `[Responsibility]` and a responsibility reaching an
outbound client are the same walk.

### Decision
- **No new level.** Dependencies are produced at `--detail members` (`Systems < Apps < Components < Members`), in the same
  analysis pass that collects members. Below `members` the analysers do no extra work. The `--detail` help of `describe` and
  `diagram`, in both CLIs, says `members` includes constructors, public members and dependencies.
- **Model**: `ComponentDetail.Dependencies: ComponentDependency list`, `ComponentDependency = { Name; Source; Via }`, where `Via`
  is the names of the unannotated types in between along the shortest chain (empty when direct). Sorted by name, then source
  (`ComponentDetail.normalise`).
- **`Uses` is removed.** `Graph.Component` has `DependsOn` (`{ Id; Via }`, the dependencies resolved to component ids of the
  same app) and `UsedBy` (the inverse). No alias.
- **Split between the analysers and Haya.Core.** Each analyser only builds a *type graph* of the analysed source: nodes
  (`TypeNode = { Key; Name; Source; Abstract }`) and edges (`TypeEdge = { From; To; Inherits }`). The walk lives once, in
  `Haya.Core/Dependencies.fs` (`Dependencies.attach`), compiled by Fable into the TypeScript tool, so both stacks follow the
  same rules by construction. The two edge extractors (`Roslyn.typeGraph` in `Haya.Roslyn/Roslyn.fs` and `typeGraphOf` in
  `Haya.Bun/analyser/analyser.ts`) are small enough to read side by side.

#### The type graph (per analyser)
- **Nodes are only types declared in the analysed source.** C#: every class, struct, record (class or struct) and interface
  (`TypeDeclarationSyntax`) in the C# projects of the solution, other projects of the same solution included. Generated code is
  skipped: files under `obj/`, `*.g.cs`, `*.g.i.cs`, `*.designer.cs`, `*.generated.cs`, and files that start with an
  `<auto-generated>` comment. TypeScript: every class (abstract or not) and interface in the program's files, without `.d.ts`,
  the default lib and `node_modules`. Free functions, modules, type aliases, enums and class expressions are not nodes.
- **The boundary is your own code.** Framework and library types (`Task`, `List<T>`, `ILogger`, `HttpClient`, `Promise`,
  `Map`), NuGet and npm packages, and referenced DLLs are never nodes. An edge to one is dropped, so the walk never goes into
  external code and `Via` only names your own types. A generic argument is its own reference: `List<CardGateway>`,
  `Task<CardGateway>` and `Promise<CardGateway>` keep the edge to `CardGateway` and drop the one to the container.
- **Edges**: A -> B when code inside A refers to B. Base types and implemented interfaces are `Inherits` edges. Every other
  reference is a use: parameter, return, field and property types, generic arguments, `new B()`, calls and member access on a
  B (the member is resolved to the type that declares it), static calls, `typeof` and `nameof`. Attributes and decorators are
  left out. C#: `SemanticModel.GetSymbolInfo` on each simple name (and `GetTypeInfo` for target-typed `new()`), normalised to
  `OriginalDefinition` and `ContainingType`. TypeScript: the checker's `getSymbolAtLocation` on each identifier, following
  import aliases (`resolveSymbol`), mapped to the class or interface that declares the symbol.
- **Nested types** belong to their outermost type, unless the nested type is annotated itself; then it is its own node.

#### The walk (Haya.Core, shared)
- For each annotated class X (a node with the name and source of a component), a breadth-first search through the graph.
- **Stop at the first annotated class.** Reaching annotated Y (not X) records X -> Y with the shortest chain as `Via`, and
  Y is not walked past: Y's own onward edges are Y's dependencies. Unannotated nodes are walked through.
- **Interfaces and abstract classes are over-approximated.** Reaching an interface or abstract class *by use* also reaches
  every type in the analysed source that implements or extends it, since the analysers cannot tell which one runs. Reaching it
  *by inheritance* does not: a class implementing `IFlow` is not linked to the other implementations of `IFlow`.
- Cycles are guarded with a visited set; there is no depth option; never a dependency on itself.
- Neighbours are visited in name, source, key order, so the shortest chain, its tie-break and the output are deterministic.
- **Scope is one app** (one analysed solution or project). Relationships between apps still come only from collaborators.

#### Outputs
- **Describe 0.6**: at `members`, each component may have `dependencies: [{ name, source, via }]`, left out when empty.
  0.0 to 0.5 still decode (no dependencies). `crc`, `backstage` and `datadog` read the files and ignore the field.
- **Graph 0.5**: a component may have `dependsOn: [{ id, via }]` and `usedBy: [id]`, each left out when empty. In the explorer,
  an app opened into its classes draws a thin dashed line per dependency between them (not selectable), and the class panel
  has **Depends on** (with `via …` muted) and **Used by** sections that select the class. All text goes through `h`.
- **Mermaid `C4Component`** at `members` draws `Rel(from, to, "uses")` between classes of one app boundary. At `components`
  it is unchanged.

### What is not understood
Traces are best effort. Whatever goes through code Haya cannot see as a type reference is not followed:
- dependency injection registrations (`services.AddScoped<IFoo, Foo>()` is a reference from the composition root, not from
  the class that takes `IFoo`; the interface over-approximation covers the common case where the implementation is in source);
- reflection, `Activator.CreateInstance`, service locators (`IServiceProvider.GetService(typeof(...))` is only followed when the
  type argument is written there);
- message buses, mediators (`IMediator.Send(new Command())` reaches `Command`, not its handler) and event handlers;
- delegates and callbacks, and any route that only passes through framework or library code;
- TypeScript free functions and module-level values: a class that calls a function that uses another class records nothing;
- annotated types found in referenced assemblies (ADR009, `--include-references`) are not nodes: they get no dependencies in
  either direction.

### Alternatives considered
- **Keep exact-match `Uses` and add dependencies next to it.** Two answers to one question; `Uses` is a strict subset.
- **A fifth level for dependencies.** Cleaner if they turn out expensive, but another option to explain while the cost is
  small (see below). It stays the way out.
- **The walk in each analyser.** It would let each language tune it, but the rules would drift and parity would test two
  implementations. Only the edge extraction is language specific.
- **Follow every implementation also when an interface is reached by inheritance.** Simpler, but it links every pair of
  implementations of a shared interface, which is noise.

### Consequences
- Describe at `members` grows: on `examples/dotnet/Example.sln` the five dependencies add about 1 KB of JSON (6,973 to
  8,032 bytes; YAML 5,046 to 5,810), about 15%.
- Analysis time on the same example: the type graph and walk take 80 to 100 ms in .NET (9 types, 35 edges, under
  `--verbose`), within the noise of a 1.4 s run; in TypeScript the walk is under 3 ms and the CLI run is the same 0.34 s.
  **Trigger to split dependencies into their own level**: when analysis time or describe size at `members` is judged too high
  on a real code base. The `--verbose` line `Dependencies: <n> types, <m> edges in <t> ms` is there to measure it.
- Breaking: describe `0.6`, graph `0.5`, `uses` replaced by `dependsOn`/`usedBy`.
- The example twins gained a three-deep outbound chain (`PaymentsController -> PaymentService -> CardGateway ->
  VisaPaymentService`), an inbound-to-responsibility chain through an interface with one implementation (`CustomerPayment ->
  IPaymentFlow -> CardPaymentFlow -> CreditCardPaymentUsecase`), a cycle (`PaymentService <-> CardGateway`) and an unannotated
  class reached from two annotated ones (`CardGateway`).
- **Future:**
  - trace queries over the dependency graph, from a collaborator to the responsibilities that lead to it, shared in Core;
  - an attribute to include extra (unannotated) classes as components;
  - DI-aware resolution (reading registrations to narrow the interface over-approximation);
  - annotated types from referenced assemblies as end points (nodes without outgoing edges).
